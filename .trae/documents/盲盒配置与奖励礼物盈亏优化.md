# 盲盒配置化 + 奖励礼物盈亏优化

## Context（背景与目标）

盲盒（爆出礼物的名称/价格）目前来自 B站 API `blindFirstWin/getInfo`，该接口**只能查当期/近期盲盒，过期盲盒查不到**，导致过期盲盒的价值/成本统计失真。

目标：
1. 把盲盒完整信息（盲盒名/单价/图标 + 礼物列表：gift_id、名称、价格、可选图标）放进 admin 配置，**永久保存在服务器，作为公共资源供每个用户读取**。
2. 当期盲盒仍走 API：由 **admin 页面触发服务器读取** B站接口并自动回填到 admin 表单，再保存到服务器（不再由用户直连 B站）。
3. 支持**额外奖励礼物**：可手动添加不在 API 列表中的礼物（名称可自由输入，也可从礼物目录联想）。奖励礼物：**成本为 0，价值按礼物价值计**，名称后显示「（奖励）」。
4. 粉丝端、主播端盲盒盈亏都要**显示并统计奖励礼物**。

## 已确认决策（用户答复）

- **存储**：扩展 `admin-config.json` 的 `blind_boxes` 为**唯一数据源**；`.data/blindbox_info/{id}.json` 降级为兼容/回退。
- **API 凭证**：admin 页面把**当前 App 登录会话的 B站 Cookie** 传给服务器接口（沿用 `RealActivityModal.tsx` 的 `getPlatform().getSessionState()` 取 Cookie 模式）。已验证无 Cookie 时接口返回 `code=-101 账号未登录`。
- **主播端口径**：不用包裹（bag_list），「靠收入记录，当日的靠弹幕监听」，与正常盲盒礼物统计方式一致，**只是成本记 0**（即奖励礼物只加价值、不加抽数/成本）。
- **粉丝端口径**：复用合成活动的包裹（bag_list）逻辑，奖励礼物按主播归属，成本 0，价值按礼物价值计；**不重写**，参照 `calcPayRecordActivityProfit` 的包裹补充实现。

## 数据模型

`src/lib/admin-config.ts`：

```ts
export type BlindBoxGiftItem = {
  gift_id: number;
  gift_name: string;
  price: number;        // 电池单价
  gift_img?: string;    // 图标（可选）
  is_reward?: boolean;  // true = 额外奖励礼物：只计价值，不计抽数/成本
};
export type BlindBoxItem = {
  id: number;
  name: string;
  icon: string;
  blind_price?: number;      // 电池；0/缺失时回退礼物目录
  gifts?: BlindBoxGiftItem[];
};
```

新增纯函数（无 fs，服务端与 Tauri 共用，防止多处漂移）`src/lib/blind-box-config.ts`：
- `buildEffectiveBlindBoxBoxes(rawBoxes) => Record<number, { id, name, icon, blindPrice, giftIds[], rewardGiftIds:Set, rewardGiftNames[] }>`

`src/lib/admin-config.ts` 增加 `normalizeBlindBoxItem / normalizeBlindBoxGift / normalizeAdminConfig`，并在 `readAdminConfig()`（读取主文件与默认模板两处）调用，兼容仅含 `{id,name,icon}` 的旧文件；幂等、不抛错。

`public/admin-config.default.json`：为各盲盒补 `blind_price` 与 `gifts`（用「从B站获取」跑一次后回填）。`gifts: []` 可接受（回退 legacy）。

## 验证（端到端）
1. **保存/读取往返**：admin 填 `blind_price`、加 2 个礼物（其中一个勾 `奖励`、名称用过期礼物自由文本）→ 保存 → 刷新仍在；查 `.data/admin-config.json`；`GET /api/config`（免鉴权）含 `gifts`+`is_reward`。
2. **旧文件兼容**：用仅含 `{id,name,icon}` 的旧 `admin-config.json` 打开 admin 不报 `TypeError`，粉丝/主播页仍可用（legacy 回退）。
3. **B站获取**：线上点 `从B站获取` 对当期盒自动回填；对过期盒返回 404；无 admin sid 返回 403；无 Cookie 返回 400。
4. **过期盒单价**：选一个过期盒，改造前后对比盲盒页 `totalSpent`（原 `drawCount×0`，现应为 `drawCount×blind_price`）与主播 tab 的 `花费`。
5. **粉丝端奖励**：账号包裹内有锁定的奖励礼物时，盲盒页出现 `xxx（奖励）` 行，`爆出` 增加、`共 N 次` 不变；切时间筛选仍在；切主播后只显示该主播的奖励。
6. **主播端奖励**：给主播送配置过的奖励礼物 → 盲盒 tab 显示 `（奖励）`，`爆出` 增加而 `花费/共 N 次` 不变；弹幕查询（今日盲盒）数值一致。
7. **镜像一致性**：同一账号对比 WEB（`/api/stats/blind-box`）与 Tauri（`stats-client.fetchBlindBoxStats`）、主播 `route` 与 `anchor-gifts-client`，切筛选（本地重算）与刷新（服务端算）后四处数值必须一致。

## 风险与不确定点
- **R1 镜像一致性（最高）**：奖励逻辑需同时存在于 `blind-box-calc.ts`、`stats/blind-box/route.ts`、`stats-client.ts`、`anchor/gifts/route.ts`、`anchor-gifts-client.ts`、`display/gift-db.ts`。缓解：只保留一份 `attributeRewardGifts` + 一份 `buildEffectiveBlindBoxBoxes`；建议把 `calculateProfit` 改为委托 `computeBlindBoxFromRecords`。
- **R2 过期盒单价未填**：admin 未填 `blind_price` 且目录无价 → 成本仍为 0、盈亏虚高。缓解：UI `⚠ 未配置单价` 提示 + 验证 4。
- **R3 未锁定包裹归属**：盲盒记录**无 `room_id`**，无法完全镜像合成活动的 `roomRuids.get(23915535)` 分支。本方案：锁定文本匹配为主、单主播兜底；**需用真实 bag_list 验证**奖励礼物是否带锁定信息，否则需扩展 `BlindBoxDrawRecord` 带 `room_id`。
- **R4 重复计数**：若 B站 `fetchBlindBoxDrawStream` 记录里也含奖励礼物，会与包裹重复。已加 `records.some(gift_id)` 保护，需实测确认。
- **R5 bag_list 为快照**：反映当前持有、不会递减；合成活动已是同语义（一致但非严格时间有界），奖励因此恒定计入不受日期筛选影响。
- **R6 无 gift_id 的奖励礼物**：过期奖励礼物可能拿不到 id，存 `gift_id:0`+名称；normalize 需保留 `is_reward` 且允许 `gift_id:0`；包裹按名称匹配，不依赖 id。
- **R7 新接口 Cookie**：body 携带 B站 Cookie，务必鉴权、不记日志、不回显；WEB admin 的 `getSessionState()` 为空，将回退到服务器现存会话（可能非 admin 本人账号），需向用户说明。
- **R8 payload 体积**：`blind_boxes[].gifts` 走公开 `/api/config`，只存必要字段（不存 `chance` 等），避免拖慢 Tauri 冷启动。
